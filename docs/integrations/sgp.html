1. Configuração por provedor

Disponibilize uma integração chamada S2Cam. Os campos abaixo são parâmetros de ativação, não novos desenvolvimentos para cada cliente.

CampoFuncionamento
Endereço S2CamURL HTTPS da instalação, por exemplo https://vibe.s2cam.com.br. Acrescente /api/integrations/v1/sgp para formar a URL base desta integração.
Chave da integraçãoFornecida pelo administrador S2Cam em Integrações. Guardar como segredo, sem exibir em logs. Enviar no cabeçalho Authorization: Bearer SUA_CHAVE. Não compartilhar chaves entre provedores.
Planos ou serviços participantesDefinir quais serviços usam S2Cam. Não enviar todos os clientes de internet indiscriminadamente. A lista de planos permitidos também pode ser limitada no S2Cam.
Situações e fuso horárioCombinar os valores reais de servico.status e seu significado. O administrador configura no S2Cam a correspondência com ativo, suspenso e arquivado. Padrão das datas nativas: UTC−3.

2. Recursos na tela do cliente no SGP

  • Criar vínculo no S2Cam: enviar o cadastro e guardar os identificadores retornados do vínculo e do grupo. A API cria o grupo e um usuário de visualização restrito a ele.
  • Consultar situação: apresentar o estado do cliente e a confirmação da última operação, distinguindo “aguardando aplicação” de “concluído”.
  • Arquivar vínculo: pedir confirmação antes de remover o acesso. O arquivamento preserva câmeras e gravações, sujeito à retenção normal.
  • Restaurar vínculo: recuperar um vínculo arquivado. O acesso segue a última situação conhecida dos serviços.

Além desses controles, o SGP deve enviar automaticamente as mudanças dos serviços participantes. Ao suspender, o S2Cam bloqueia o cliente e encerra seus vídeos abertos. Câmeras exclusivas de grupos suspensos têm gravação e análise pausadas. Uma câmera compartilhada com outro grupo ativo continua atendendo esse grupo.

A reativação preserva as configurações anteriores. Câmeras que já estavam desativadas continuam desativadas; gravações manuais encerradas não reiniciam sozinhas. Se houver vários serviços do mesmo cliente, um serviço ativo mantém seu grupo ativo.

Login e senha inicial: CPF sem pontuação. O cliente precisa escolher uma nova senha antes de acessar câmeras. Eventos e reenvios não redefinem a senha escolhida. CPF já utilizado exige confirmação do vínculo pelo administrador; a integração não assume o controle de um usuário existente.

O contrato atual exige CPF válido. Cadastros com CNPJ precisam de uma regra combinada para enviar o CPF do responsável; CNPJ não é convertido em senha.

3. Enviar eventos

POST {BASE}/webhook, com JSON e autenticação Bearer. São aceitas as ações nativas cadastrar, atualizar, alterar_plano e alterar_status. Envie os campos completos em todas as ações.

{
  "acao": "cadastrar",
  "data": "2026-10-13T10:00:00.123456-03:00",
  "cliente": {
    "id": "123",
    "cpfcnpj": "52998224725",
    "nome": "Cliente de exemplo"
  },
  "contrato": { "id": "456" },
  "servico": {
    "id": "789",
    "status": "ATIVO",
    "plano": { "id": "10" }
  }
}

ATIVO é um exemplo: configure as situações reais do SGP no S2Cam. Situações desconhecidas são recusadas. Use a data original da mudança, não a data de cada tentativa. A API aceita ISO 8601 com fuso ou o formato nativo 13/10/2026 10:00:00.123456, no fuso configurado.

curl --request POST "$S2CAM_BASE/webhook" \
  --header "Authorization: Bearer $S2CAM_KEY" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: evento-unico-do-sgp" \
  --data @evento.json

As variáveis representam a URL base e a chave guardada na configuração do conector. Não coloque chaves reais em código-fonte, arquivos de exemplo ou histórico de comandos.

Compatibilidade com o Gateway Genérico do SGP

O recebimento suporta o formato nativo do Gateway Genérico. Se a equipe SGP reutilizar esse mecanismo, configure os planos participantes e os cabeçalhos abaixo. Os controles de arquivar/restaurar e o acompanhamento das operações devem usar os endpoints explícitos.

{
  "url": "https://DOMINIO_DA_INSTALACAO/api/integrations/v1/sgp/webhook",
  "headers": {
    "Authorization": "Bearer SUA_CHAVE",
    "Content-Type": "application/json"
  }
}

Referência oficial do SGP. O S2Cam não altera diretamente o cadastro ou o banco do SGP.

Endpoints — relativos a {BASE}

MétodoCaminhoUso

Codifique identificadores usados na URL com percent-encoding. Cada chave acessa somente os clientes de sua integração; consultas de outra integração retornam 404.

4. Confirmação, fila e tratamento de erros

{
  "gateway_id": "identificador-do-vinculo",
  "gateway_params_extra": "identificador-do-grupo",
  "operation_id": "identificador-da-operacao",
  "status": "PENDING",
  "customer_status": "ACTIVE",
  "repeated": false
}

HTTP 200 confirma que o evento foi gravado, não que todos os serviços já foram ajustados. Guarde os identificadores. Consulte GET {BASE}/operations/ID até receber COMPLETE. PENDING significa que a aplicação continua em andamento; IGNORED indica evento antigo ou substituído por outro mais recente.

Mantenha uma fila durável no SGP. Em falhas de rede, 429 ou 503, reenvie o mesmo evento com espera progressiva — 5, 15, 30 e 60 segundos — respeitando Retry-After, quando presente. Preserve a data e, se utilizado, o Idempotency-Key. Um identificador reutilizado com dados diferentes retorna 409.

RespostaAção esperada do conector
400Revisar campos, CPF, plano, data ou situação não mapeada.
401 / 403Revisar chave, ativação e autorização. Não entrar em repetição contínua.
404Revisar vínculo e instalação; um cliente ainda não cadastrado precisa de cadastrar.
409Revisar conflito de cadastro, evento ou vínculo arquivado. Não trocar a data apenas para esconder o conflito.
429 / 503 / falha de redeManter na fila e tentar novamente com espera progressiva.

Reenvie periodicamente o estado atual dos serviços participantes, preservando a data da mudança. Essa reconciliação recupera divergências após falta de comunicação. A API não busca automaticamente o banco do SGP.

5. Homologação do conector único

  1. Configurar um provedor e uma chave próprios de homologação.
  2. Cadastrar cliente de teste; conferir grupo, usuário e troca obrigatória da senha inicial.
  3. Reenviar o cadastro e confirmar que não duplica o cliente nem redefine sua senha.
  4. Suspender com vídeo aberto; aguardar COMPLETE e conferir encerramento do acesso e pausa dos serviços exclusivos.
  5. Conferir que outro cliente continua assistindo à câmera compartilhada.
  6. Reativar e conferir configurações restauradas, sem ativar câmeras originalmente desativadas.
  7. Testar eventos fora de ordem, vários serviços, arquivamento/restauração, chave substituída e queda de comunicação.
  8. Ativar o mesmo conector em outro provedor, mudando apenas configuração e chave.

O backend S2Cam foi validado em ambiente isolado com HTTP, PostgreSQL, vídeo e gravação reais de fontes sintéticas. A homologação de ponta a ponta com o SGP deve ser realizada em conjunto, antes de enviar clientes reais.
